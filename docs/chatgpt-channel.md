# ChatGPT 通道（接力 1b，#99）

驿窗经常浩自己 Chrome 里登录的 chatgpt.com 接通 ChatGPT 聊天。三段：

```
chatgpt.com 标签页（内容脚本）⇄ 插件后台 ⇄ Chrome Native Messaging ⇄ 转接程序 ⇄ 驿窗（本机套接字）
```

## 固定标识

| 项                     | 值                                                                                                                                                                          |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 插件目录               | `src/apps/chrome-extension/`（开发者模式「加载已解压的扩展程序」）                                                                                                          |
| 插件 id                | `fjjbgamejbdjdaddinacpbmaeokinbjl`（manifest 的 `key` 固定，换目录加载 id 不变）                                                                                            |
| Native host 名         | `com.postpane.chatgpt`                                                                                                                                                      |
| host manifest（macOS） | `~/Library/Application Support/Google/Chrome/NativeMessagingHosts/com.postpane.chatgpt.json`，`allowed_origins` 只写 `chrome-extension://fjjbgamejbdjdaddinacpbmaeokinbjl/` |
| 转接程序               | 随驿窗打包；Chrome 启动它时第一个参数是 `chrome-extension://<id>/`                                                                                                          |
| 驿窗套接字             | `<数据目录>/chatgpt/extension.sock`（目录 0700、套接字 0600，同 local_tools）                                                                                               |

## 分帧

两段都用同一种分帧：4 字节小端长度 + UTF-8 JSON（Chrome Native Messaging 的格式；驿窗到 Chrome 一帧不超过 1 MB）。转接程序只原样搬运，不解析内容。

## 消息

每条都是带 `type` 的 JSON 对象。时间一律毫秒时间戳（`at`）。

### 插件 → 驿窗

| type     | 字段                                                                                                       | 说明                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hello`  | `version`, `extensionId`                                                                                   | 插件后台连上后第一条                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `tabs`   | `conversations: [{id, open, hidden}]`                                                                      | 名单里各会话标签页状态，变化时发                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `turn`   | `phase: "start" \| "complete"`, `conversation`, `title`, `prompt`, `promptId?`, `reply`, `messageId`, `at` | 任一会话一轮开始 / 完成（#145 起不限名单；还没有会话 id 的新会话不报）。`complete` 时 `reply` 是整理好的 Markdown 全文，`prompt` 是这一轮用户消息全文，`title` 是会话标题（标签页标题去掉「 - ChatGPT」等后缀，可能为空）。应 `reread` 补报的 `complete` 另带 `reread: true`                                                                                                                                                                                                                                                                                                       |
| `opened` | `requestId`, `ok`, `conversation?`, `title?`, `promptId?`, `reason?`                                       | 回应 `open`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `sent`   | `requestId`, `ok`, `promptId?`, `reason?`, `pressed?`                                                      | 回应 `send`。没送成时 `pressed` 说发送按钮点没点过（#466）：`false` 是确定没点（正在回答、没找到输入框、内容对不上、按钮没亮、标签页没加载好、会话不在名单里），`true` 是点了但没见开始；不带这一项是说不清（发送途中标签页被关、页面抛了异常没说点没点，或旧版插件）。试了两次的合起来报：任一次点过是 `true`，两次都明确没点才是 `false`，其余不带 |
| `reread` | `conversation`, `outcome`, `hidden`, `active`, `minimized`, `fronted`                                      | 回应 `reread`（#457，插件 0.2.4 起）：这次重读找到了什么（`outcome`）、标签页当时怎样。`outcome` 取值：`told`（补报了 `turn complete`）、`undrawn`（最新一轮已答，回信没画出来，切到前台也没读到）、`streaming`（还在写）、`waiting`（还没答，或回信还在变）、`unloaded`（历史一直没加载完）、`unreachable`（补注入脚本后标签页仍不应答）、`unopened`（后台打开的标签页 30 秒没报到）。`hidden` 是页面最近一次报的是否在后台，`active` 是不是它窗口里的当前标签，`minimized` 是窗口是否最小化，`fronted` 是这次有没有把它切到前台再问。驿窗写进 `turns.jsonl`（`phase: "reread"`） |
| `shadow` | `conversation`, `why`, `at`, `outcome`, 其余见「影子读取」 | 影子读取（#488，插件 0.2.6 起，开关开着才有）：这次从对话数据里读到了什么。驿窗只记一行，不据此做任何事 |

### 驿窗 → 插件

| type     | 字段                                | 说明                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `watch`  | `conversations: [id]`, `shadow?`               | 名单整体替换。名单只决定哪些会话能送话、算「审核」。`shadow: true`（#488）：影子读取开着，见「影子读取」；没有这一项就是关 |
| `open`   | `requestId`, `text`, `project?`     | 新开会话（`project` 是 ChatGPT 项目页网址，给了就在项目里新建），填 `text` 发出，拿到 `/c/<id>` 后回 `opened`，并把它自行加进名单（不等下一条 `watch`）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `send`   | `requestId`, `conversation`, `text` | 给名单里的会话送话；标签页没开就在后台打开 `https://chatgpt.com/c/<id>` 再送                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `focus`  | `conversation`                      | 把这个会话的标签页切到前台（没开就打开）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `reread` | `conversation`                      | 重读名单里的会话（#356）：标签页先核对自己显示的是这个会话；最新一条回复已写完（600 毫秒内正文不变，和正常上报同一标准）、而且排在最新一条用户消息之后，就按 `turn complete` 再报一次（带 `reread: true`）；正在写或还没回就不报。问完回一条 `reread` 说找到了什么（#457，0.2.4 之前不回应）。标签页没开就在后台打开；内容脚本断了（插件重新加载过）先补注入再问；页面还没画出最新提问之后的回复、也不在生成（历史还没加载完，`loaded: false`）就每 2 秒再问，最多再问 5 次。「最新一轮」按页面里各条消息单元键第一次出现的顺序定（页面把对话放两份：隐藏的一份各轮齐全、回信不画，显示的一份只画屏幕附近几轮，#410）；最新一轮已答、回信只在隐藏那份里时不报，先把对话滚到底；标签页在后台（ChatGPT 不在后台标签页画新内容），就把它在自己窗口里短暂切到前台再问，最多 3 次、每次隔 1.5 秒，问完切回原来在前台的标签页（这期间常浩自己换过标签就不动），不把 Chrome 窗口提到最前 |

`reason` 取值：`not-watched`、`no-composer`、`busy`（正在生成）、`send-failed`、`composer-mismatch`（输入框里的字和要送的话对不上：多出旧稿，或少了一截、发送键却亮着，比如长文被转成附件，#429）、`timeout`、`tab-closed`。插件收到 `send-failed`、`composer-mismatch` 会把标签页切到前台、清空输入框再试一次；输入框外的附件块清不掉，留着附件时两次都报 `composer-mismatch`，交常浩到页面上移除。

`promptId`（#410，插件 0.2.3 起）：ChatGPT 自己给一轮提问的消息编号，插件从页面上那一轮提问格子的 `data-chatgpt-search-message-ids` 读出。`opened` / `sent` 带的是这次送出的话变成的那条提问（送出后最多等 3 秒，页面画出新提问才有；新开会话时，拿到会话地址后再向标签页要一次）；`turn` 带的是这一轮回答的那条提问。页面没画出来就不带，驿窗退回比对文字。实测（2026-11-19）：同一轮的提问和回答共用编号前缀（`<轮>:0:user` / `<轮>:2:assistant`），刷新后不变。提问格子里有自己的文字就算提问：有文字气泡的读气泡；ChatGPT 把很长的粘贴变成附件「粘贴的文本 (1).txt」时没有气泡，读格子里的文件名（不算读屏文字和按钮）；只有读屏文字、按钮的格子算历史还在加载。

## 驿窗这一端

- ChatGPT 作为一个客户端（`agents/src/chatgpt`，id `chatgpt`），会话 id 为 `chatgpt:<会话id>`，回跳目标 `chatgpt-conversation`（交给插件 `focus`，插件不通时用浏览器打开 `https://chatgpt.com/c/<id>`）。
- `turn complete` 变成一条 completion 事件，侧栏照常弹「新回复」回执；回复全文不截断。
- `turn start` 变成一条 running 的 session-observation，会话显示「在答」，直到回复完成；ChatGPT 只报一次开始，没有心跳，15 分钟还没完成（多半是标签页关了）就不再算在答。它和回复一样写进 hook 收件箱（ChatGPT 没有直连应用的钩子通道，收件箱是唯一的路）；收件箱只为「自己的通道报回合」的客户端收这类记录（#206 之前一律拒收，「在答」从没显示过）。
- 对话与审核（#145）：名单里的会话（驿窗经 `open` 开的）算「审核」，其余是常浩自己开的「对话」；两种事件都带 `review`，快照里的 ChatGPT 会话带 `review: true | false`。只读得到 Chrome 里 chatgpt.com 的对话，手机端、Mac 桌面应用看不到。
- 插件装上、更新或重新加载时（#206）：Chrome 不给已开着的 chatgpt.com 标签页装新内容脚本，旧脚本跟插件断开，这些标签页里的对话就一直报不上来（接力会话由插件新开标签页，不受影响）。所以插件后台在 `runtime.onInstalled` 时给每个已开的 chatgpt.com 标签页补装 `page.js`、`content.js`（要 `scripting` 权限）；同一页面再装一次时，旧的一份先停下、新的一份接手，不重复报；断开的旧脚本发消息出错就自己停下。
- 新会话在首页发出，ChatGPT 开始回答时地址里还没有会话 id，那次 `turn start` 不带 `conversation`；地址变成 `/c/<id>` 时若仍在生成，插件带上新 id 再报一次 `turn start`，接力才会进入 `working`。
- 名单 = 驿窗经 `open` 新开过的会话，存 `<数据目录>/chatgpt/watched.json`（1c 的接力会话也在其中，见下）。
- 设置 · 智能体插件页有「ChatGPT（Chrome 插件）」一行：登记 host manifest、显示是否连上。
- 插件版本校验（#493）：驿窗打包时把同一仓库 `src/apps/chrome-extension/manifest.json` 的版本编进去（`platform/src/clients/chatgpt/version.rs`），插件 `hello` 报的版本和它比。一样时设置行写「已连接 · <版本>」；插件旧了，设置行「需要重新加载插件」、「AI 接入」状态章橙色「可用 · 插件要重新加载」；插件新了（驿窗没重装），分别是「需要重装驿窗」「可用 · 驿窗要重装」。这时会话调 `relay_to_chatgpt` 照常发出，回复的 `message` 末尾多一句提醒；连上时日志（`<数据目录>/logs/postpane.log`）写一行。版本是点分数字逐段比，末尾的 0 不算（0.2 等于 0.2.0）；没报版本或认不出的不提示。
- 两条线程（#440）：插件说的每句话都由这条连接唯一的读线程读出来，回调在读线程上只记账（`Desk::observe`），别的都不做；接着要做的事（转回发起会话、请 ChatGPT 补写末尾格式、核对 PR 当前提交，`Desk::drive`）和通知侧栏（`republish`）都交给另一条线程 `postpane-handoff-driver`，它做事期间又被叫到的合并成再做一次；线程没起来或没了，下次被叫到时重新起，做事时出错不会让线程退出，它不在时由数据线程每次完整快照兜底推进（最迟 30 秒一次）。两条约束：`send` / `open` 要等插件的确认，确认只能由读线程带回，所以读线程不能自己经这条通道发送并等确认；通知侧栏（`Backend::refresh_handoffs` → `projection`）自己也会推进，还要等后台锁，而数据线程可能正拿着这把锁等插件的确认，所以读线程也不能通知侧栏。

## 1c 接力（#71）

一个 Claude Code 会话把工作交给一个 ChatGPT 会话审核，两边绑成一组「接力」（代码里叫 handoff，避开已经指 API 中转站的 relay），之后的往返都在这两个会话里接着聊。

### 接力记录

- 存 `<数据目录>/chatgpt/handoffs.json`（目录 0700、文件 0600，整份替换写），保留最新 200 条：`{id, title, claudeSession, cwd, chatgptConversation, status, error?, createdAt, updatedAt, rounds, phase, phaseAt, steps, brief?, roundsFrom?}`，时间是毫秒时间戳。#257、#258 加的字段（`roundsFrom`、步骤的 `prompt` / `delivery`）旧文件里没有，读进来为空，不影响已有记录。
- `status`：`opening`（新会话正在打开）→ `open`（已绑定会话）或 `failed`（打开失败，`error` 写原因）；同一个 Claude 会话发起新审核、或常浩点「结束接力」时改成 `closed`。等常浩处理的接力（回信已到、已转回，或自动往返已停）放着 24 小时没动静（`IDLE_END_MS`，按 `phaseAt` 与 `updatedAt` 较晚的算；后台续接中的不算），生成快照时驿窗自动结束，时间线记一步 `end`（`auto`，写「等常浩处理 24 小时没动静，驿窗自动结束接力」），不给发起会话送话（常浩 2026-11-14 选甲：开着的单子在纸飞机上累积到 21）。一个 Claude 会话、一个 ChatGPT 会话同时只属于一条未结束（opening / open）的接力。
- `phase`（批 A，#120）：`sending`（正在送，新会话在开）→ `delivered`（插件确认已送到，对方没开始）→ `working`（插件报这一轮开始）→ `replied`（回信到了，还没转回）→ `returned`（已转回 Claude）；另有 `ended`、`failed`。`phaseAt` 是进入这一阶段的时间。「送到了」只认插件的 `opened` / `sent` 回应，「审完了」只认 `turn complete`。
- 侧栏小人：网页 ChatGPT 没有会话可数，接力处于 `working`（ChatGPT 正在回答）时，算作 ChatGPT 所在那一格（与 Codex 共用的 OpenAI 小人）在工作，播「工作中」；回信到了、失败或结束就停（`crates/hud/src/vendors.rs` 的 `relays_answering`、前端 `packages/hud/src/relays-answering.ts`）。
- 左滑发起（批 B，#124；归因与持久化 2026-11-07）：「正在进行」里本机 Claude 会话左滑点「审核」「讨论」，宿主经 Claude Code 插件给该会话留一段固定的话，请它自己整理后调 `relay_to_chatgpt`。每次左滑有自己的编号（`L` 开头），写在留的话里，请会话调用时填进 `launch` 参数；只有带着这个编号、来自同一会话的调用才算这次左滑办了，新开审核或续进已开的审核都算，同会话别的接力不算。左滑记录存在 `chatgpt/launches.json`，驿窗重启后照样认得，排队中的不会再留一次。状态：等待或已领取算「排队中」，会话开始处理算「已送进会话」；插件文件在被看到领取之前就没了，算「状态不明」，不说成已领取；一小时没领取算过期；领取后一小时（从领取时算）没发起接力算停滞；状态不明一小时没等到接力算「没等到」。这几种结局在那一行显示半小时，之后可以再左滑。快照字段 `relayLaunches`。插件「先标记已领取再提交」保持不变，防止重启后重复提交，领取后中断也不自动重发。
- `steps`：每一步 `{at, kind, text?, points?, verdict?}`。`work` Claude 做完一轮（`text` 是 `summary`，没给就用标题）、`ask` 驿窗送给 ChatGPT 且已送到（`text` 是原话摘录）、`reply` ChatGPT 回信（`points` 是回信里编号列出的意见，最多 12 条；`verdict` 从最后的「结论：通过 / 需修改」读出 `pass` / `revise`；最新一条回信全文保留，最多 64 KB，供「转回 Claude」用）、`back` 转回 Claude、`again` 请 Claude 交回复审（这两种另带 `prompt`、`delivery`，见下「回执」）、`fail` 没送出去、`end` 结束。快照里的步骤只带 600 字以内的摘录，不带原话指纹。
- 去重：同一段文字刚送到 ChatGPT、还没回信时，再送一次（Claude 等超时重试）不重复发，返回 `status: "repeated"`；转回 Claude 同理。同一条接力同一时间只有一段话在路上，并排的第二次直接拒绝（「上一段还在送」）；同一个 Claude 会话同一时间只能发起一次，「结束接力」也要等路上那段送完。
- 回执（#257，只管「回 Claude」这一段）：每一步转回 Claude 的话（自动与手动「转回 Claude」、「再审一轮」、思维评审收口转回）用固定 id 交给插件，`prompt` 记在那一步上：`<接力 id>-b<回信步序>`（转回）或 `-a<回信步序>`（再审一轮），满足插件的文件名规则。同一步不论重试、重复点、自动和手动同时触发，还是重启丢了记录后再来，都用同一个 id；插件那边已有同 id 的话时返回「用过了」（`IdentityConflict`），驿窗当作已送过，不再送第二份。只有插件明确放弃了（被拒、过期、取消），下一次才换新 id（尾巴加 `-1`、`-2`）。驿窗生成快照和自动往返处理回信时（`Desk::track`），用插件的状态文件（`Lines::left`）跟进 `delivery`：`waiting` 排队中 → `taken` 已领取 → `started` 已开始，接力卡在「转回 Claude」「请 Claude 交回复审」那一行后面写出来；排着队的话被领走时清掉 `queuedAt`，「等 Claude 交回复审」的 2 小时从领走时算。`refused` / `expired` / `cancelled`：马上交还常浩并写明原因（自动往返开着就停下，`halt` 写原因；关着就记一条 `fail`），转回那一步的阶段退回 `replied`，卡上重新出现「转回 Claude」。`QUEUE_WAIT_MS`（1 小时）只在读不到插件状态时兜底。
  - 取舍：上游 Agent HUD 的「结果不明不重发」只用在回 Claude 这一段。送给 ChatGPT 那一段照旧「30 秒没回话算失败、可重试」：ChatGPT 网页靠插件在标签页里填字发送，没有队列、也没有可按 id 查的回执，重试比漏送好；迟到的 `sent` 仍按 #223 补记，不会记两次。

### 接力状态（状态转移与不变量，7a 批 1）

一张接力的状态由 `status`（4 种）和 `phase`（7 种）一起决定，另有 `auto` / `halt`（自动往返开着还是停着）、`queuedAt`、`wakingSince` 几项只管等待，不改这两项。所有改动都在 `Book`（`host/src/handoff/book.rs` 及 `book/`，7a 批 2 从 platform 搬来；通道的 `config.json` 读写和私有目录留在 platform `chatgpt/files.rs`）里；宿主 `Desk` 只调用它。测试在 `host/src/handoff/book/tests/states.rs`：下表每一行对应一条 `tNN_` 测试；`t10` 用固定种子随机跑 300 组、每组 120 步（各种移动、各种时间间隔混着来），每一步后检查全部不变量。改了一行转移或一条不变量，表和测试一起改。

能出现的组合：

| status | phase | 怎么来的 |
|---|---|---|
| `opening` | `sending` | 新发起（`begin`）、重试（`retry`） |
| `open` | `delivered` / `working` / `replied` / `returned` | 绑上会话之后的一轮轮往返 |
| `failed` | `failed` | 没打开（`failed`、`expire`、`interrupted`） |
| `closed` | `ended` | 结束（`end`、`passed`、`idle`、审查链转走） |
| `closed` | 被顶替时的阶段 | 同一会话发起新接力、或别的接力绑上同一个会话时，旧的只改 `closed`，`phase` 停在原处（`t01`、`t02`） |

转移（前提不满足的调用不做任何事、返回 false）：

| 移动 | 前提 | 结果 | 测试 |
|---|---|---|---|
| `begin` | 无 | 新接力 `opening/sending`；同会话原来进行中的改 `closed`（阶段不变） | `t01` |
| `opened` / `opened_late` | `opening`；或 `failed`、还留着 brief、没被同会话更新的接力顶替 | `open/delivered`，记 `ask`；绑同一会话的其他进行中接力改 `closed`（阶段不变） | `t02` |
| `failed` / `expire`（打开超 2 分钟）/ `interrupted`（重启时还在开） | `opening` | `failed/failed` | `t03` |
| `retry` | `failed`，同会话没有进行中的接力，也没被同会话更新的接力顶替（F-01） | `opening/sending`，`attempt` 加 1 | `t04` |
| `working` | 进行中、绑着这个会话，阶段 `sending` / `delivered` | `working` | `t05` |
| `replied` | 进行中、绑着这个会话，阶段 `sending` / `delivered` / `working`，或有没答的送话 | `replied` | `t05` |
| `returned` | 进行中 | `returned`，`rounds` 加 1 | `t05` |
| `asked` / `format_asked` | 进行中 | `delivered`（`asked` 另加 1 轮、清掉等待） | `t05` |
| `undelivered` | 进行中，没送到的是最新一段转回 | 是「转回」且阶段 `returned` 时退回 `replied`；停下自动往返（已停着就记一步失败） | `t06` |
| `end` | 进行中或 `failed` | `closed/ended` | `t07` |
| `passed` | 进行中 | `closed/ended` | `t07` |
| `idle` | `open`、不在唤醒，阶段 `replied` / `returned`（或停着的 `delivered` / `working`），闲置超 24 小时 | `closed/ended` | `t07` |
| `close_others` | 同一审查链上别的进行中接力，或还可能迟到打开的失败接力 | 进行中的改 `closed/ended`；失败的仍是 `failed`，只清掉 brief、不能再绑会话 | `t08` |
| `stop` / `overdue` / `unconfirmed` / `stop_undrawn` | 进行中、自动往返开着 | `auto=false`、`halt` 写原因，`status`/`phase` 不变 | `t09` |
| `resume` / `evidence_in` / 续接时自动恢复（只恢复驿窗自己停的） | 进行中、停着 | `auto=true`、`halt` 清空 | `t09` |
| `queued` / `woke` / `awake` / `delivery` / `told` / `round` | 各自的前提 | 只改等待、回执、轮数，`status`/`phase` 不变 | `t10` |

不变量（随机跑的每一步都查，`t10`）：

- I-01 `status` 是 `failed` 当且仅当 `phase` 是 `failed`。
- I-02 `phase` 是 `ended` 时 `status` 一定是 `closed`；反过来不成立（被顶替的保留原阶段）。
- I-03 `closed` 是终点：之后 `status`、`phase` 都不再变。
- I-04 `opening`、`failed` 没绑会话；`open` 一定绑着会话。
- I-05 `auto` 开着当且仅当 `halt` 为空。
- I-06 同一个 Claude 会话最多一张进行中的接力。
- I-07 同一个 ChatGPT 会话最多绑一张进行中的接力。
- I-08 `rounds`、`attempt` 只增不减，`steps` 只追加不删。
- I-09 `phaseAt` 不晚于 `updatedAt`。

缺口与约定：

- F-01（2026-11-21 随机跑发现，常浩回「修 F-01」，当天修好）：同一会话先后两张接力都没打开，重试较旧那张、较新那张又迟到打开，曾会有两张进行中的接力。现在 `retry` 和 `opened` 一样不认被同会话更新的接力顶替的那张，接力卡上点它的「重试」显示「这次接力不能重试」。测试 `f01_…`。
- `Book` 不拦在 `opening` 上调用 `asked` / `returned` / `format_asked`（只要求进行中），所以「`opening` 一定是 `sending`」不写成不变量，靠宿主只在打开后续接。

- 侧栏票根上的章（2026-11-07 常浩定，`packages/hud/src/relay-stamps.ts`）：ChatGPT 票根的蓝色「审」只在 ChatGPT 真的在看时盖——接力开着、处于 `delivered` / `working`、没被停（`halt` 为空）、送达不到 `REPLY_WAIT_MS`（30 分钟）；被停掉或交还常浩的不盖。送达超过 30 分钟还没回信的（不论停没停）改盖红色「未审」，点 ChatGPT 那一格直接打开那个 ChatGPT 对话（悬停照旧出面板）。「未审」让位（#213）：ChatGPT 格有更要紧的事要说——在答（常浩自己的对话或接力在答）、有回信待你看——时不盖「未审」，脚注照常显示；空下来再盖回去。「未审」挂满 `LINGERS_MS`（2 小时，同悬停面板不再列出该审核的 `STALE_REVIEW`）不退场，边框像「审」在答时那样向外发散（蜡红、长方框），直到接力结束。Claude 票根的「回」（#218 改，常浩定甲「脚上一枚，答优先」）：和「审」同一枚蓝色方章，盖在 Claude 票根的脚上，原脚注让开，不发散；这时 Claude 的脚也换成接力纸加航空斜纹，和 ChatGPT 在审时一样。Claude 自己同时有待答 / 待批时，脚上只盖红「答」/「批」，「回」让开，接力纸和斜纹保留。有接力处于「已回复」等常浩处理时显示；自动往返停着时到的回信照样转回之后（`returned`、`auto` 关、有 `halt`），同样盖这枚「回」，外观动效不变（#410 S1，场景 `relay-held-back`）；停在上限的不盖，那是 ChatGPT 票根的「停」（#409）；判了通过的会自动结束，所以只剩「需修改」交还常浩、还没处理的，卡上点「结束接力」或转回 Claude 后撤掉。

### 自动往返（批 2，#72）

- 开关：新接力默认开（`auto: true`）；#72 之前的记录读进来是关的。卡头「接力」旁标「自动往返」，因别的原因停了（超时、回信认不出、送话失败等）标琥珀色「未完暂停」（悬停看原因；常浩 11-19 由「自动已停」改名，#409），停在上限时不标、由圆章「停」说明，底部多一个「暂停自动」/「继续自动」。
- 回信到了（`replied`）且开着时，驿窗按结论自己走（`Desk::drive`，插件报 `turn complete` 后立即跑）：
  - 「结论：通过」：先把回信全文转回 Claude（`back` 步带 `auto`，写明这是终局、驿窗已结束接力、不用再送审，请它合并前顺手改掉 P2/P3 等非阻断意见并向常浩汇报），再自动结束接力，`end` 步带 `auto`；自动往返关着或已停时也照样转回并结束（2026-11-07 常浩定：判了通过的接力一直开着，Claude 票根上的「回」撤不掉；2026-11-12 起通过也转回，之前只结束、发起会话收不到）。`end` 步写明回信是已转回、已排进待发送队列（还没送到），还是两次都送不到且排队也失败（照样结束，请常浩告诉会话）；
  - 审查出口「返修」且本次授权周期还没到上限：把回信全文转回 Claude（与「转回 Claude」同一段话），`back` 步带 `auto`；Claude 改完自己调 `relay_to_chatgpt`，进入下一轮；
  - 受审版本对不上或 PR 已有新提交：转回请 Claude 用当前提交重送，自动往返不停（见上「版本锚点」）。
  - 到顶仍不是通过、补过格式仍认不出末尾几行、读不到 PR 当前提交、送达未确认：先把回信全文转回 Claude，末尾写明这是终局、自动往返已停、交常浩决定、不要再调 `relay_to_chatgpt`，再停下交还常浩（`stop` 步，`halt` 写原因），卡上照常可「再审一轮」「结束接力」（2026-11-12 起，之前不转回，发起会话收不到）。停止原因同时写审查结果和回信去向（已转回 / 已排队还没送到 / 没能转回），送不到不再改写成「转回失败两次」而丢掉原因。转回文字由回信本身算出（`Handoff::outcome`，不看自动往返开没开），所以自动转回和常浩点「转回 Claude」是同一段话；同一条回信只转回一次（同一个 `-b` id 加文字指纹），再点按钮不送、也不多记一步。交常浩的几种终局，转回文字分两层写：现在可以做（读意见、整理要点和返修方案；思维评审可起草决策记录，待定的不记成已定），先不要做（改代码、再送审、合并 PR）。
  - 终局回信排进待发送队列后不做后台续接（接力已结束或已停，交常浩的事不在后台替会话开工）：会话一打开就领走；插件放弃了（被拒、过期、取消）时，已结束的接力在时间线加一条「接力已结束，但最后一条转给 Claude 的话……会话没收到」（手动结束时排着的普通转回或「再审一轮」也一样，所以不称终局回信），还开着的照 #257 退回「已回复」并记一条 `fail`，停止原因不变。
  - 还没回信就出的错（#318）：新会话打开失败（当场失败、2 分钟没打开、驿窗重启时还在打开）、ChatGPT 30 分钟没回信和回信没画出（#457），生成快照时（`Desk::tell`）各通知发起会话一次：出了什么错、接力现在的状态、会话该做什么（不要自己重送，向常浩说明；打不开的由常浩在卡上「重试」，且只说「目前记为失败」，因为插件之后补报打开成功（`opened_late`）时接力会接回、回信照常转回；没回信的，之后回信照常收、照样转回发起会话：工程审查写「通过」的照常结束接力，其他结论写明下一步等常浩决定，#410）。出错步带结构化标记 `cause`（`notOpened` / `noAnswer` / `undrawn`），不靠说明文字认；认的是最近一条带标记、之后只追加过 `fail` 的步，且接力还停在那个状态（回信、重试、继续自动之后就不再通知）。走转回同一条通道，id 为 `<接力 id>-n<步序>`，送不进去就排进待发送队列，不后台续接；发之前先占住这次接力的发送权（`claim`），再按当前状态核对一遍（含同一会话是否已开了新接力，`superseded`）；从核对到发完，账本的其他改动（插件报来的迟到打开和回信、「重试」「继续自动」、超时检查）都先等着（`Desk::quiet`），所以通知发出时说的仍是实情；期间被压下的回合（`turn_waits`）发完后补收（`caught_up`），不丢。每个出错步只送一次（记在 `told`）；通知起点存在 `chatgpt/notices.json`（新版第一次启动时写下），之前的出错不补发，之后出的错即使驿窗没来得及通知就重启，也会在重启后补发一次。卡上不加新行：那一步（`fail` 或自动 `stop`）的说明和 `halt` 末尾补「已发到 Claude 会话」「已排进 Claude 会话的待发送队列」或「没能通知 Claude：原因」（只表示送进了会话，不表示会话已处理）。迟到的回信照常收，阶段不变。Claude 2 小时没交回复审、转回排队 1 小时没领不通知（前者卡在会话自己，后者会话本就收不到）。
- 出错与处理（送回 Claude，L-14，#175、#255、#257）：先经插件直接送话，用这一步的固定 id（#257）。送不到时看会话的插件签到：
  - 签到写着已结束（桌面版在内存紧张时会回收空闲会话的 Claude 进程，日志 `CliGovernor pressure evicting`；打开或点开会话只会「预热」，不会重启进程），或超过 `WAKE_AFTER_MS`（3 分钟）没签到：驿窗立即**后台续接**（只对 Claude Code 会话；Codex 发起的接力走 Codex 自己的队列，#280）——按桌面版的会话记录（`claude-code-sessions/**/local_*.json`，用 `cliSessionId` 对上）取工作目录、模型、思考强度和权限模式，跑 `claude -p --resume <会话> --permission-mode <模式>`，把回信全文连同处理要求交给它；时间线记 `back` 和 `wake` 两步（`auto`），`back` 的送达状态记为已开始，快照字段 `wakingSince` 表示正在跑。只有 `auto`、`acceptEdits`、`bypassPermissions` 三种权限模式会续接，其余后台没人点允许，直接交还常浩。续接跑完后 Claude 已调 `relay_to_chatgpt` 交回复审，就照常往下走；跑完还在等 Claude（没交回复审或出错退出），停下交还常浩。实测：会话被停后续接 12 秒完成，之后在桌面版里给它发消息，应用续接同一个会话号，看得到并接上那一轮（证据 `evidence/2026-11-07-headless-resume/`）。续接进行中桌面版界面是否实时显示、和常浩同时在应用里发消息的并发情况未验证。
  - 签到只是过期（多半是电脑一时卡顿）：马上重试一次，两次的错误各记一条 `fail` 步（`auto`）；仍失败就用同一个 id 把这段话排进该会话的待发送队列（`Lines::queue`，不要求会话在线，#255），记 `queuedAt`，阶段照常是 `returned`、自动往返不停。插件领走后按 #257 跟送达状态。排队 3 分钟后仍没领、且会话已停或 3 分钟没签到，撤回排队（插件的 `.cancel`）再后台续接；撤回不了（已被领走）不续接，防止送两遍；后台续接起不来就按「取消」交还常浩，回信等常浩再转。从没签到过的会话可能根本没装插件、正在运行，不续接，排队 `QUEUE_WAIT_MS`（1 小时，与插件的留话寿命一致）没被领走就停下交还常浩。排队失败也停下交还常浩。
  - 停着时到的回信（#410 S1，2026-11-19 常浩选「S1 按推荐做」）：自动往返关着（驿窗自己停的或常浩暂停的）时到的回信，生成快照或自动往返处理回信时（`Desk::drive` / `catch_up`）照样把全文转回发起会话一次（`back` 步带 `auto`，同一个 `-b` id 去重），末尾写「驿窗的自动往返停着（停因），这封回信照样转给你，下一步交常浩决定」，附「现在可以做 / 先不要做」；自动往返保持关着。「通过」照旧走自动结束（上面第一条），思维评审收口照常写收口。之前这类回信一直停在侧栏等常浩点「转回 Claude」，发起会话不知道（Fable 5.2 评估 22 单里 16 单如此）。转不进去也排不进队列时，卡上记一步 `trouble`（「回信没能转回 Claude 会话……请在接力卡上点『转回』」），不自动重试。判定在 `Handoff::held_answer`（`host/src/handoff/book/held.rs`），转回在 `host/.../handoff/held.rs`。
  - 新送审重开（#410）：自动往返是驿窗自己停的（最近一步 `stop` 带 `auto`），下一轮送审确认送到时（`Book::asked`），先记一步 `resume`（`auto`），清掉 `halt`，再记送审；停因说的是上一轮，这一轮照常自动往返。常浩手动「暂停自动」的不重开，`relay_to_chatgpt` 的返回如实写「常浩暂停了这张接力的自动往返：回信到了照样转回这个会话，但会写明下一步等常浩决定」（`Handoff::paused_by_person`）。到上限的送审不经常浩授权本来就收不进（审核门），所以不会被这条绕开。
  - Claude 再调 `relay_to_chatgpt` 交回复审时清掉 `queuedAt`、`wakingSince`。ChatGPT 30 分钟没回信（`delivered` / `working` 超过 `REPLY_WAIT_MS`）、Claude 2 小时没交回复审（`returned` 超过 `FIX_WAIT_MS`，后台续接从续接时起算）都停下交还常浩，在生成快照时检查。驿窗重启时自动往返保持原样，不再暂停（常浩 2026-11-14，之前一律先暂停、要点「继续自动」）：回信只从「回信已到」转回一次、转回步记在卡上，所以重启不会重送；重启前到了还没转回的回信，由生成快照时的补推（`Desk::catch_up`）接着转回；重启前的后台续接不再跟踪。常浩点「继续自动」或授权专项续审（`extra`）后，等着的回信立即处理，各项等待从点下时重新计时（`phaseAt`，排队中的 `queuedAt` 也是），不会下一次快照又停（#223；专项续审 2026-11-14 补上，之前续审旧单当场就报「Claude 2 小时没交回复审」）。常浩手动「转回 Claude」/「再审一轮」送不进去时，同样排进待发送队列、记 `queuedAt`，排队也失败才报错。驿窗重启时写下的停止原因和结束说明，按设置里的界面语言写（那时 Core 还没跟随语言设置）。
- 记录：每一步的 `at`、谁做的（`auto` 表示驿窗自动做的，没有就是常浩点的）、出错原文与处理方式（`fail` / `stop` 的 `text`）都在 `handoffs.json`，每轮耗时由相邻步骤的时间相减得出。

### 本机工具通道

- 一条连接一个线程，同时最多 8 个，超了立即回「忙」；一个慢请求（等 ChatGPT）不挡别的。
- 转接程序（`agent-hud-engine --app-channel`）按方法定等待（`request_with_timeout`）：`chatgpt_open` 100 秒（打开最多 90 秒再留 10 秒），`chatgpt_send`、`relay_to_chatgpt` 40 秒（送话最多 30 秒），其余照旧 40 秒；转接程序也把应用没认出 id 的回答（如「忙」）补上请求的 id。MCP 那头 `relay_to_chatgpt` 等 55 秒（`EngineClient.request` 新增的 `timeoutMs`，默认仍 45 秒）。

## 影子读取（#488，接力根治第 1 批）

回信照旧从页面画面读，那一路作数。影子读取另加一路：插件在 chatgpt.com 页面里读页面自己用的对话数据，把读到的摘要报给驿窗，驿窗只记录，不据此认领、转回或停下任何接力。用来攒证据，决定以后要不要改成读对话数据；来由和探测结果见 [接力第1批探测结果](design/接力第1批探测结果-2026-11-20.md)。

- **开关**：`<数据目录>/chatgpt/config.json` 的 `dataShadow`，默认没有（关）。设成 `true` 后重启驿窗生效：驿窗在 `watch` 里带 `shadow: true`。设置里没有这个开关的界面。
  - 打开时：插件把 `data.js` 登记进 chatgpt.com 页面自己的运行环境（`chrome.scripting.registerContentScripts`，`world: "MAIN"`，`document_start`），并给已经开着的每个 chatgpt.com 标签页补装一份。所有 chatgpt.com 标签页都会装上它，包括常浩自己聊天的页面；在那些页面里它只旁听、不读数据。补装进去的页面读到的不可信（见「可信」），刷新后由登记的那份重新装上才可信。登记失败、或有没被丢弃的标签页装不进去，记成「打开未完」（`shadowArm.pending`，带装不进去的标签页），驿窗每发一次名单就重试一次，插件后台重启后也接着重试（#488 审查 P2-03）。
  - 关掉时：先撤掉登记（`getRegisteredContentScripts` 回查确认撤掉了），再到每个开着的 chatgpt.com 标签页里调用它的 `stop()`；然后等开关切换前已经开始的读取、登记和补装全部结束（插件后台记着在途的每一件），再撤一次登记并回查（收掉在途的登记），再到每个标签页调用一次 `stop()`，报的是这第二遍的结果。开关切换一件一件排队做，关开关不会和还没做完的开开关同时跑；每一次切换在每个异步步骤之后都核对代次，期间又切换了，就停在那一步，交给后一次去做；写进存储的开关状态是这一次要的状态（第 3、4 轮审查 P1-02）。关开关时，只要存的状态、未完的撤销、或回查到的登记里有任何一样说可能还登记着，就照常撤销。不论是哪种情形触发的撤销，第一步都先在存储里记下「撤销未完」（`shadowDisarm.pending`），全部确认之后才清掉；查不到标签页列表也算没完（`unlisted`），插件后台中途被终止，重启后收到名单会接着撤（第 5 轮审查 P1-04）。`stop()` 中止页面里正在发的请求（每次读取一个 `AbortController`）、清掉登录信息、不再旁听、不再读；页面的 `fetch` 没被别人再包过就放回原样，被包过就只透传。停用是永久的：句柄上没有重新启用的入口，同一个页面再装一份也只会让开（见「怎么调用」），所以关掉再打开后，开着的页面要刷新才重新读。开关每切换一次，插件后台的「代次」加一；读取每一步之后都核对代次，变了就停，不补装、不报读到的内容，只报一条 `superseded`（#488 审查 P1-02）。被 Chrome 丢弃（`discarded`）的标签页没有页面在跑，重新加载时也不会再装。别的够不着的标签页、或登记没撤掉，记成「撤销未完」（插件 `chrome.storage.local` 的 `shadowDisarm.pending`），驿窗每发一次名单就重试一次。撤销的结果报给驿窗一条 `why: "off"` 的记录（开关关着也记）。
  - 开关切换（关→开、开→关）都让停读状态重新开始。插件后台重启后，开关以驿窗下一次发来的名单为准；停读状态和读取账本从插件存储恢复。
- **登录信息**：`data.js` 旁听页面自己发往 `/backend-api/` 的请求，把其中的登录请求头留在自己的闭包里：页面读会话那个请求按前缀留（`authorization`、`originator`、`chatgpt-*`、`oai-*`、`x-openai-*`，记 `login: "same"`）；没见过它时用页面别的请求的，只留探测见过的那 11 个名字（`"other"`）。还没旁听到登录信息时不读，报 `no-login`。登录信息不交给内容脚本、插件后台或驿窗。
- **怎么调用**：页面上没有任何消息入口。`data.js` 在 `window` 上放一个不可改写、不可删除的句柄（属性名 `__postpaneData`，有 `read`、`prove`、`stop` 三个函数：`read` 读数据、`stop` 停用；`prove(nonce)` 只给插件后台核对可信用，证明这个句柄知道凭证里的随机码，不读任何数据。它挡不住先于驿窗控制页面环境的其他扩展，见「风险和防不住的」）。插件后台按这个名字直接取，不经过 `Symbol.for` 这类页面能换掉的东西；这个属性一旦放上，页面改原型、换 `Symbol.for` 都指不到别处（第 3 轮审查 P1-01）。插件后台用 `chrome.scripting.executeScript`（`world: "MAIN"`）直接调用它，结果经插件内部通道带回，页面上的脚本看不到，也伪造不了回传（#488 审查 P1-01）。`data.js` 跑起来时句柄已经在了（以前装过的那份，或页面、别的扩展先放的），它一律不用、什么都不做，脚本的结果是 `present`；装上了是 `installed`。句柄是 `data.js` 做的第一件事：先放上（放不上就报 `unavailable`，不当成已有句柄，也不留凭证），再做其余准备；准备完之前、或准备中途出错，读取只回 `outcome: "failed"`，页面也没法再放自己的同名句柄。可信要句柄答出 `data.js` 凭证里的随机码（见「可信」），所以骗过它只剩一类：先于驿窗控制页面环境的其他扩展（抢先放句柄，或事先改掉内建方法、在 `data.js` 放句柄时换掉它并控制随机码），属常浩已接受的风险（第 5 轮及新周期第 1–3 轮审查 P1-01，见「风险和防不住的」）。插件后台补装时看这个结果。
- **取下原生方法**：`data.js` 一跑起来就取下读取要用的原生方法（`fetch`、`Response.prototype.text` 和 `status`、`JSON.parse`、`crypto.subtle.digest`、`TextEncoder.prototype.encode`、`Headers`、`URL`、`AbortController`、`Reflect.apply`，以及请求计数用的 `Date.now`），读的时候只用取下的这份；页面之后改 `Date.now` 也抬不高「每页 10 分钟 12 次」的上限（新周期再审第 2 轮审查 P2-13）。登记的那份在 `document_start` 跑，早于页面自己的脚本，所以页面之后改这些原型，影响不到读取。数组、字符串这类公共原型没有一一取下（见「风险」）。
- **可信**（`trusted`，#488 审查 P1-01）：要有正面证据才算可信，「不在不可信名单里」不算，也不靠比较两个时钟（第 3、4 轮审查）。插件后台登记 `data.js` 时，在同一次 `registerContentScripts` 里一起登记 `mark.js`（`world: "ISOLATED"`，`document_start`，两份要么都登记、要么都不登记）。`mark.js` 跑在插件自己的隔离环境里，页面和别的扩展都碰不到。`data.js` 放好句柄之后、页面还在加载时，生成一个只有自己知道的随机码，写在一个插进文档的空元素 `<postpane-installed data-token=…>` 上当凭证；`mark.js` 看到恰好一个凭证、随机码格式对，才把随机码收进隔离环境（`postpaneDataToken`），并拿掉所有凭证。读完之后，插件后台按同一个 `documentId` 先从隔离环境取随机码，再现做一个随机数，让页面里的句柄算「随机码:随机数」的 SHA-256（`prove`），和自己算的对上才可信。页面里共享的 DOM 别的扩展也能改，所以光看凭证在不在不算数：别的扩展插的凭证，页面的句柄答不出它的随机码；`data.js` 没跑、句柄没放上、`mark.js` 比它先跑、凭证不止一个，都没有可用的随机码，一律不可信。如果真实 Chrome 里隔离环境那份总是先跑，所有读取都会是不可信，对账里一眼能看出来，要装机实测（新周期第 1、2 轮审查 P1-01）。读完之后，插件后台用 `executeScript` 在同一个隔离环境里、按同一个 `documentId` 查这个标记：有标记，说明这个页面是登记生效之后才加载的，`data.js` 在页面任何脚本之前就装上了，才加 `trusted: true`；没有标记、取不到 `documentId`、或返回的不是同一个 `documentId`，都是 `trusted: false`。插件后台补装 `data.js` 不补装 `mark.js`，所以补装过的页面没有标记。补装过的页面另记在 `chrome.storage.local` 的 `shadowDocs` 里：补装结果是 `installed` 的记「晚装」，一律 `trusted: false`；是 `present` 的记「冲突」，页面说的一概不要，只报 `outcome: "conflict"`。`shadowDocs` 最多记 200 个，淘汰掉的页面仍要有标记才可信，所以淘汰不会让它变成可信。这个标记由插件后台加，不信页面说的。对账只把 `trusted: true` 的计入门槛。
- **页面里的限制**（不论谁调用句柄）：只读这个标签页正显示的会话；会话编号和提问编号都要是 UUID；每个页面 10 分钟内最多发 12 次请求，超了报 `limited`。每发一次请求之前现取登录信息，停用后取不到，报 `stopped`；每个 `await` 之后都再核对一次是否已停用，停用了就报 `stopped`，不再发第二次（更宽的）请求。
- **读什么**：`GET /backend-api/conversations/<会话>?num_turns=2&include_has_versions=true`（页面自己进会话时发的同一个接口，页面取 10 轮）。驿窗记下的提问不在这 2 轮里、前面还有时，再取一次 10 轮，仅此一次。所以一次读取是一次或两次请求。
- **怎么认回信**：在 `messages` 里找编号等于提问编号、角色是 `user` 的那条；它后面到下一条用户消息之前是这一轮；回信是这一轮里 `channel` 为 `final`、`metadata.turn_exchange_id` 和提问相同的最后一条助手消息。`status` 为 `finished_successfully`、`end_turn` 为 `true`、`metadata.is_complete` 为 `true`、`metadata.finish_details.type` 为 `stop` 四样都满足才算写完（`written`）。回信的正文必须是 `content.content_type` 为 `text`、`content.parts` 为全是字符串的非空数组，不是就报 `unreadable`（`missing` 写 `final.content.content_type` 或 `final.content.parts`），不算写完（#488 审查 P2-06）。提问没有 `turn_exchange_id`、`page_info.has_previous_page` 不是布尔值、缺用到的字段时报 `unreadable` 并列出缺哪些。不用 `metadata.parent_id`（不完整）。
- **什么时候读**：都由事件触发，不靠页面计时器。三种原因：页面那一路报了回信（`why: "complete"`）；驿窗发起重读、页面问过之后（`"reread"`）；驿窗的话发出 20 秒后（`"writing"`，看回答生成中数据长什么样）。每条提问每种原因最多一次，所以每条提问最多读三次、最多六次请求。读取账本按「会话:提问 → 读过的原因」存在插件的 `chrome.storage.local`（`shadowLedger`，最多记 200 条提问），先记账再读，插件后台重启后同一条提问不会再读；按提问分开记，后发的提问不会占掉前一条的次数，前一条迟到的事件也不会动后一条的（#488 审查 P1-03、P2-05）。插件后台启动时从存储恢复账本、提问和补装记录；恢复失败（或存的不是约定的样子）就一律不登记（已经登记的撤掉，开着的页面里那份停用）、不补装、不读、不覆盖存储里的旧账，每次该读时只报 `ledger-unavailable`，直到插件后台下次启动恢复成功（#488 审查 P1-03，第 3 轮补上「不登记」）。撤销没成功、或有没被丢弃的标签页停不了，记进 `shadowArm`（`unregistered`、`failed`），开关开着时每次名单都再试，不当成已清理（第 4 轮审查 P1-03）。
- **读哪条提问**：20 秒后那一次读的是那段话发出后变成的那条（定时器建立时就记下，之后又发了话也不变，#488 审查 P2-05）；页面报回信那一次读页面带的那条；驿窗重读那一次读驿窗的话最近变成的那条。这个会话还不知道提问时，页面报回信带的那条记下来给之后用；已经知道的不被页面报的覆盖。同一个会话接连送了两次话、后送的先回来时，记下的是后送那次的提问（第 3 轮审查 P2-09）。开关关着、或送话途中开关切换过，送话的结果什么都不记；20 秒后的那次读取也只在这段时间里开关没切换过时才做，开关一切换，还没到点的都取消（第 3、4 轮审查 P2-08）。编号不是 UUID 的不认。都不知道时不读，只报 `no-prompt`。只读名单里的会话、只在插件连着驿窗时读、只问正显示这个会话的标签页（没有就报 `no-tab`）。
- **什么时候停**：任何一次不是 200，或请求发不出去，这个会话不再读；401、403、429 则所有会话都不读。不重试。停的状态存在插件的 `chrome.storage.local`（`shadowStops`），插件后台重启后仍然有效；把开关关掉再打开才重新开始。
- **两头校验**：插件后台只认摘要里约定的字段和类型，有一个不对就整条记成 `invalid` 并列出哪些字段；驿窗写入前再按字段白名单过一遍，未知或类型不对的字段丢掉、记个数（`dropped`）。编号（会话、提问、回信）只认 UUID；`why`、`outcome`、`pageOutcome`、`login` 和消息的 `role`、`channel`、`status`、`type`、`finish` 只认约定的词（`data.js` 的 `KINDS`，认不出的由 `data.js` 记成 `other`）；`asyncStatus` 的取值还没摸清，只记有没有（有就是 `other`）。跨字段：摘要里的 `asked` 必须是插件后台要它找的那条，`askFound` 为真时 `prompt` 必须等于它；驿窗那头 `askFound` 为真而 `prompt` 和 `asked` 不同，就把这两个字段丢掉。数值两头一样严：`status` 100–599，`turns` 只能 2 或 10，`tries` 只能 1 或 2，各种计数最多 10 亿，`sha` 只认 16 位小写十六进制（第 3 轮审查 P2-10）。所以记录里没有自由文字，也放不进一段任意的 ASCII（#488 审查 P1-01 和白名单意见）。
- **`shadow` 消息和记录**：驿窗把每条 `shadow` 按白名单过滤、加上 `heardAt`，追加成 `<数据目录>/chatgpt/shadow.jsonl` 的一行。不在名单里的会话、开关关着时不记（`why: "off"` 的撤销记录除外）；超过 4096 字节的不记。文件已存在时必须是普通文件、只有本人能读写，不是就不写（#488 审查 P2-04）。字段：

  | 字段 | 含义 |
  |---|---|
  | `conversation`, `why`, `at`, `asked` | 会话、原因（见上，另有 `off`）、插件发出的时间、要找的提问编号 |
  | `pagePromptId`, `pageMessageId`, `pageChars` | `why` 为 `complete` 时：页面那一路认到的提问编号、回信编号、回信字数，用来对比 |
  | `pageOutcome` | `why` 为 `reread` 时：页面那一路这次重读的结果 |
  | `outcome` | `read` 读到了；`conflict` 页面的句柄不是 `data.js` 自己的，页面说的不要；`superseded` 读到一半开关切换了，结果不报；`ledger-unavailable` 读取账本没恢复，没读；`http` 不是 200（带 `status`）；`error` 请求没发出去；`unreadable` 结构读不懂（带 `missing`）；`no-login` 还没有登录信息；`limited` 页面里的请求上限到了；`stopped` 页面里那份已停用；`failed` 页面里那份句柄已放上、其余准备没做完；`no-script` 页面里没有 `data.js`（这时插件补装一份，下次再读）；`other-conversation` 标签页显示的不是这个会话；`no-tab` 没有显示这个会话的标签页；`no-prompt` 不知道是哪条提问，没读；`unreachable` 标签页里调用不了；`invalid` 页面回的不是约定的摘要（带 `fields`）；`why: "off"` 时为 `disarmed` 或 `disarm-pending` |
  | `status`, `turns`, `tries`, `bytes`, `ms`, `hidden`, `login` | 状态码、取了几轮、发了几次请求、返回的 UTF-8 字节数（#488 审查 P2-07）、耗时、当时标签页是否隐藏、用的哪一套登录信息 |
  | `messages`, `more`, `asyncStatus` | 返回的消息条数、前面还有没有、会话级状态 |
  | `askFound`, `prompt` | 找没找到要找的提问、实际用的那条提问 |
  | `after`, `exchange`, `last` | 提问后面这一轮有几条消息、它们的 `turn_exchange_id` 是否都和提问相同、最后一条的角色 / 类别 / 状态 / 内容类型 |
  | `final` | 回信：`id`、`status`、`endTurn`、`complete`、`finish`、`chars`（字数）、`sha`（正文 SHA-256 的前 16 位）；没有就是 `null` |
  | `written` | 回信是否写完（四样都满足） |
  | `trusted` | 页面那一路给出的结果才有：页面加载时就装上 `data.js` 的为 `true`，后来补装的为 `false`（见「可信」） |
  | `tabs`, `stopped`, `failed`, `unregistered` | `why: "off"` 时：调用了几个标签页、几个确认停用、几个够不着、登记是否已撤掉 |
  | `dropped`, `heardAt` | 驿窗过滤掉的字段数、驿窗收到的时间 |

  记录里没有回信正文，没有登录信息。
- **对账**：`node scripts/relay-shadow-report.mjs` 把 `shadow.jsonl` 和 `handoffs.json` 对一遍，按切换门槛列出够不够。只有 `trusted: true` 的读取计入门槛；`trusted: false` 和 `conflict` 的不进门槛、也不算漏读，单独数出来。`no-script` 那次只是待补证：之后（按 `shadow.jsonl` 里的先后，不按时间戳，同一毫秒的也分得清，第 3 轮审查 P2-02）要有一次可信的读取，同一会话、要找的是同一条提问、实际找到的就是它（`prompt` 相同、`askFound` 为真）、回信编号和页面那一路报的相同，而且读成、写完，才算补上，没补上的算漏读；认到的提问和补上的那几次要找的提问，都要能在 `handoffs.json` 里找到，也是门槛之一（#488 审查 P2-02）。
- **风险和防不住的**：这不是公开接口，结构和频率限制都没有承诺；`data.js` 包了一层页面的 `fetch` 来旁听，页面能察觉到。影子证据的来源可信只做到这一步：补装的页面标成不可信、句柄冲突的页面不要、读取用页面加载前取下的原生方法、可信要句柄答出凭证随机码的挑战。剩下两类防不住，常浩决定接受，只靠 `trusted` 标记加门槛排除兜底：
  - 页面在 `data.js` 装好之后改数组、字符串这类没有一一取下的公共原型，能影响 `data.js` 对数据的整理，给出结构合法的假摘要；也能让页面里的请求计数失效（计数用的是数组的 `push`、`shift`），再反复调用句柄的 `read`，绕过「每页 10 分钟 12 次」的上限。这 12 次是正常页面下的限制，不是挡得住页面篡改的安全上限；要保证上限，得另做不依赖页面原型的计数（2026-11-21 接受；新周期再审第 1 轮审查 P2-12 补写这一后果）；
  - 任何先于驿窗在页面环境（MAIN 世界）执行的其他扩展：它能抢先放好句柄，也能事先改掉 `Object.defineProperty`、`crypto.getRandomValues` 这类内建方法，在 `data.js` 放句柄时换成自己的句柄、让随机码变成它已知的值，于是答得出挑战，影子读取会被判成可信。随机码挑战挡不住这种对页面环境的预先控制，不再靠加层修补（2026-11-21 先接受「抢先放句柄」，同日新周期第 3 轮审查后经驿窗侧栏回「甲：扩大接受再审1轮」，扩大到这一整类）。
  接受的理由：现有正式那一路（读页面画面）完全由页面脚本画出来，页面顶层脚本同样能伪造，所以影子那一路对页面脚本的可信度不低于现有正式路径；「来源绝对可信」对任何读 chatgpt.com 的办法都做不到。两头校验保证假摘要也只能是约定字段里的编号、计数和标记；影子记录不驱动任何接力行为；切换之前要在真实环境核对。所以默认关，出现任何异常就停，读页面那一路不受影响。

## 页面结构（2026-11 新版 chatgpt.com，探针 #95）

- 一轮 `[data-turn-key]`；回复 `[data-chatgpt-search-unit-key$=":assistant"]`；用户消息 `[data-user-message-bubble]`；读屏标题 `h4[data-conversation-role]`、`.sr-only` 整理时跳过。
- 正文组件 `data-d-component`：text / title / list / list-item / code / table / table-row / table-cell；加粗 `[data-d-default-strong]`。
- 代码块两种画法：CodeMirror `.cm-content[data-language]`（行是 `.cm-line`），或 `pre > code`（语言在块头文字里）。
- 输入框 `.ProseMirror[contenteditable=true]`；发送 `form button[type=submit]`；生成中同位置是「停止」按钮。
- 送话用粘贴（保留段落），按行切成每段不超过 6000 字依次贴到末尾（不在双码元字符、`\r\n` 中间切；只有空白的一段不单独切出，并进下一段；连续空白超出 1000 字才单独切开，任何一段都不超过 7000 字），每段等输入框（去空白）净增长到这段的全部可见字才贴下一段，3 秒没到就算没贴进。ChatGPT 会把单次粘贴超过某个长度（在 8000 到 1 万字之间）的文字转成附件「粘贴的文本.txt」（2026-11-19 实测按字符数算：8000 字仍是正文，1 万字成附件；切点落在代码围栏里也照原样逐行保留，输入框不画代码块）：转了附件，页面上没有用户消息气泡、也没有原文：插件 0.2.3 之前因此不报 `turn complete`（#429，L-59）；0.2.3 起插件认附件那一格、驿窗按提问编号认领（见上「按编号认」），附件也收得回，但 ChatGPT 审的是附件文件、页面上看不到原文，所以发送侧仍分段，让送审保持正文。贴之前输入框已空、发送键却亮着（上次留下的附件），或有一段没贴全、贴完去空白后和原文不是同样的字，发送键却亮着，都不发，报 `composer-mismatch`；粘贴不被页面接收时退回整段 `insertText`，这时输入框与原文（去空白）相差超过 40 字也报 `composer-mismatch`（#435 审查 P1-01）。
- 新回复先出一个空的占位块，答案随后写进同一个块、同一个 `messageId`。插件只在回复不为空、而且 600 毫秒内没再变化时才报 `turn complete`；否则占位块会被当成答完，同一 `messageId` 的真回复随后被当成已报过而丢掉（2026-11-07 接力 `h1a1b1fed89e00`，L-18）。
- 页面选择器只写在 `src/apps/chrome-extension/page.js` 一处；改版失效时插件报 `no-composer` 等原因，驿窗退回半自动。
