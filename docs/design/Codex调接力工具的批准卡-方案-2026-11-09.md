# Codex 调接力工具的批准卡：原因与方案（2026-11-09）

来由：#282 实测时，测试用的 Codex 线程 `01a1be3c-e125-7411-a308-4169ce8921a9` 两次调 `relay_to_chatgpt` 都「不返回」；Codex 放弃后，侧栏 Codex 格上的批准卡（「批」章）还挂着，盖住了「回」章。本文只调研、出方案，没改代码。

证据目录：`~/Library/Application Support/postpane/evidence/2026-11-09-codex-relay-approval/`

- `rollout-excerpt.txt`：测试线程会话记录摘录（行号对应 `~/.codex/sessions/2026/11/09/rollout-2026-11-09T10-57-03-01a1be3c-….jsonl`）
- `tools-list.jsonl`：对已装的 `PostPane --mcp` 发 `tools/list` 的原始回包
- `codex-approval-mode-values.txt`：Codex 对按工具批准配置的校验输出
- `codex-app-server.txt`：Codex app-server 进程的启动时间
- `postpane-setting.txt`：驿窗「审批等多久」设置的当前值

## 结论

1. **要批准是 Codex 自己的规则，驿窗钩子只负责转送。** `relay_to_chatgpt` 声明了 `openWorldHint: true`（会把内容送到外部服务），Codex 在 `on-request` 下对这类 MCP 工具逐次要批准；`send_message` 等其他写工具声明的是 `openWorldHint: false`，不用批准。Codex 0.167 支持按工具设批准方式：`[mcp_servers.agent-hud.tools.relay_to_chatgpt] approval_mode = "approve"`。
2. **#280 那次也要批准，只是 35 秒内有人批了。** 今天的第一次调用一直没人批，Codex 等了 7 分钟后结束了这一轮。
3. **卡没撤，是因为这张卡其实一直有效。** Codex 结束这一轮时没有取消这次调用。驿窗设成了「一直等」，而 Codex 的钩子挂在常驻的 app-server 下面，进程没变，L-36 的父进程检查不会触发。13:07 这张卡被批准后，Codex 把 22 分钟前已经放弃的调用补跑了一遍，往 ChatGPT 会话重复送了一轮。所以过期的卡不只是挡住「回」章，批准它还会让调用迟到执行。
4. **推荐**：先做 1A，在 Codex 配置里给这一个工具设免批准，从源头消掉这类卡。再做 2A，作为所有 Codex 批准卡的兜底：那一轮结束了，驿窗就替常浩拒绝并撤卡。2A 会改到「一直等」的行为，开工前要先发改动确认。

## 一、为什么 Codex 调 `relay_to_chatgpt` 要批准

### 1. 这一轮的批准设置

测试线程每一轮的 `turn_context` 都是 `approval_policy = on-request`、`approvals_reviewer = User`、沙箱 `danger-full-access`（`rollout-excerpt.txt` 中 turn_context 各行）。`~/.codex/config.toml` 第 6 行也是 `approval_policy = "on-request"`，`[mcp_servers.agent-hud]`（第 321 行）只有 `command`、`args` 两项，没有按工具的设置。

### 2. 两个工具声明的注解不同

对已装的 `/Applications/PostPane.app/Contents/MacOS/PostPane --mcp` 发 `tools/list`，结果如下（`tools-list.jsonl`）：

| 工具 | readOnly | destructive | openWorld | 实测要不要批准 |
|---|---|---|---|---|
| `relay_to_chatgpt` | false | false | **true** | 要：03:15:29 调用，03:16:05 才执行，调用本身只用了 0.04 秒（会话记录第 45、47、53 行） |
| `send_message` | false | false | false | 不要：从调用到完成 0.05～0.07 秒，三次都是（第 21/23、62/64、330/332 行） |
| `start_session` | false | false | false | 本线程没调 |

`openWorldHint: true` 写在 `src/apps/mcp/src/index.ts:549-553`，是 #71（`5375029`，2026-11-06）建这个工具时加的，语义是对的：这个工具确实会把说明送到常浩的 ChatGPT。

**推断（没读到 Codex 源码）**：Codex 默认的 `auto` 规则是只读工具免批准，非只读工具里只要声明了 destructive 或 openWorld 就要问。依据是上表中两个写工具一个要批、一个不要批，唯一的差别就是 `openWorldHint`。

### 3. 批准请求怎么变成侧栏的卡

- `~/.codex/hooks.json` 的 `PermissionRequest` 挂的是 `'/Applications/PostPane.app/Contents/MacOS/PostPane' --permission-hook codex`，`timeout: 86400`。这是驿窗装的钩子，配置见 `src/crates/agents/src/codex/hooks.rs`（`timeout: 86_400`、`reviewer_gate: true`、`settles_in_transcript: false`）。
- 驿窗收到请求后，先确认这一轮的批准人是常浩本人（`approvals_reviewer = User`，见 `src/crates/platform/src/hooks/unix.rs:228-233`），再登记成卡片等待（`unix.rs:234-264`）。驿窗不判断哪些工具要批准，只接 Codex 已经决定要问的请求；如果卸掉这个钩子，Codex 照样会问，只是改在它自己的界面里问。

所以问题出在 Codex 的 MCP 工具批准规则上，不在驿窗钩子。

### 4. Codex 能按工具设免批准

用 Codex app-server 实际在跑的那份 CLI 校验配置（`codex-approval-mode-values.txt`）：

```
codex-cli 0.167.0-alpha.3.2
unknown variant `bogus`, expected one of `auto`, `prompt`, `writes`, `approve`
    in `mcp_servers.agent-hud.tools.relay_to_chatgpt.approval_mode`
```

`approval_mode = "approve"` 能通过校验。Codex 二进制里同时有服务器级的 `default_tools_approval_mode`，还有批准框里的「Allow and don't ask me again / Run the tool and remember this choice for future tool calls」。**推断**：`approve` 就是「以后都直接执行」，和在 Codex 自己的批准框里点「不再询问」的效果一样。这一点要在 1A 实施时实测确认。

### 5. #280 当天为什么能「直接成功」

那次并不是免批准。会话记录显示：

- 03:15:29 调用（第 45 行），03:16:00 Codex 报「Script running with cell ID 4 / Wall time 31.0 seconds」（第 47 行）；
- 03:16:05 调用完成，工具本身耗时 0.04 秒（第 53 行）。

中间约 35 秒在等批准，而且在模型轮询放弃之前就被批准了，所以看上去「成功」。是谁批的没有查实，驿窗不记录批准人。今天第一次调用（12:45:27，第 87 行）之后，模型连续轮询约 7 分钟（第 89～267 行），12:52:40 结束这一轮。第二次调用（13:01:38，第 282 行）在 13:02:53 被模型终止（第 328 行「Script terminated」）。

另外，Claude 侧没碰到这个问题，是因为 `~/.claude/settings.json` 的 `defaultMode` 是 `bypassPermissions`，不会弹出批准。

## 二、Codex 那一轮结束后，批准卡为什么还挂着

### 1. Codex 结束这一轮，不会取消已经在等批准的调用

| 时间（北京） | 事件 | 出处 |
|---|---|---|
| 12:45:27 | 第一次调用 `relay_to_chatgpt`（轮 `01a1bea0…`），侧栏出现「批」卡 | 会话记录第 87 行；#282 交接 |
| 12:52:40 | 这一轮 `task_complete`，模型说「工具持续未返回」 | 第 271～275 行 |
| 13:01:38 → 13:02:53 | 第二次调用，模型等了 75 秒后终止 | 第 282、328 行 |
| 13:04:11 | 主会话改为直接调驿窗 MCP，建单 `h1a1beb129a000` | `handoffs.json` |
| **13:07:14** | **第一次调用在已经结束的轮 `01a1bea0…` 下完成**，结果是 `status: sent`，送进同一个接力单 | 第 340 行 |
| 13:07:14 / 13:07:20 | `h1a1beb129a000` 时间线多出一组 `work`、`ask`，ChatGPT 又回了一次「收到」 | `<数据目录>/chatgpt/handoffs.json` |

也就是说，这张卡在 13:07:13 左右被批准，Codex 照常执行了这次调用，尽管调用它的那一轮早在 14 分钟前就结束了。是谁批的同样没有查实。第二次调用被终止后一直没执行，它当时有没有出过卡、什么时候撤的，也没查实。

### 2. 驿窗这边，没有任何一条会撤掉这张卡

驿窗只在下面五种情况撤卡（`src/crates/platform/src/hooks/unix.rs:240-264`，`client_unix.rs`），这次一条都不满足：

| 撤卡条件 | 这次为什么不满足 |
|---|---|
| 常浩在侧栏答了 | 13:07 之前没人答 |
| 等待时间到了 | `approvalWaitMinutes = 0`（`postpane-setting.txt`），即「一直等」，截止时间是 `i64::MAX`（`src/crates/core/src/requests.rs:17-25`） |
| 钩子连接断开 | Codex 给钩子的超时是 86400 秒，Codex 自己没取消，钩子进程一直连着 |
| 会话记录显示在客户端里答过了 | Codex 的 `settles_in_transcript: false`，驿窗不读 Codex 会话记录来判断 |
| 钩子的父进程变了（L-36） | 父进程是常驻的 Codex app-server（pid 83594，10:56:22 起一直在跑，见 `codex-app-server.txt`）。L-36 处理的是进程被杀，这次结束的只是一轮，进程还在 |

### 3. 什么时候应该撤

当发出这条请求的那一轮已经结束（`task_complete` 或被中断），模型就不再等结果了，这张卡也就失去意义。驿窗登记的请求里本来就有 `turn_id`（`src/crates/agents/src/hooks/request.rs:234`，来自钩子 payload 的 `turn_id`），Codex 会话记录里每轮结束都有带同一 `turn_id` 的 `task_complete`，两边能对上。

撤卡时只拿掉卡片还不够，必须同时给 Codex 一个**拒绝**。如果只回 `{}`（驿窗现有的「交还客户端自己问」），调用在 Codex 那边还挂着，之后无论在哪里批准，都会像 13:07 那样迟到执行。

## 六、1A 实施结果（2026-11-09 13:20–13:30，常浩回「做 1A」）

- 配置：`~/.codex/config.toml` 在 `[mcp_servers.agent-hud]` 后面加了 `[mcp_servers.agent-hud.tools.relay_to_chatgpt]` 和 `approval_mode = "approve"` 两行。原文件备份在证据目录的 `config.toml.before-1a`。
- **新开的线程生效**：13:28 用驿窗 `start_session` 新开 Codex 线程 `01a1bec7-a276-…`，调用到完成只用了 0.02 秒（会话记录第 19～21 行），没出批准，建单 `h1a1bec7ca0802`。
- **已经开着的线程不生效**：13:22 在 10:57 开的老线程 `01a1be3c…` 里调用，13:22:01.147 照样触发了 `PermissionRequest` 钩子（`logs_2.sqlite` 里有 `hook/started`，没有 `hook/completed`），60 秒没返回。13:23:12 模型终止等待（`terminate`），钩子进程随之结束，侧栏没有留下卡片，这次调用也没有执行。这一点补上了第五节「第二次调用有没有出过卡」：模型终止脚本单元会取消调用、撤掉卡片；只有模型没终止、直接结束这一轮时（12:45 那次），卡才会一直挂着。
- `codex exec` 做的两组测试（`approve` 和对照组 `auto`）都直接执行，说明 exec 本身就没有交互批准，这两组不能当证据（L-38）。它们多建了两张测试接力单：`h1a1bec6d6da00`、`h1a1bec74c5b01`。
- 结论：1A 有效，但只对新开的线程生效。2A 仍有必要，用来兜底老线程和其他要批准的工具：模型不终止就结束这一轮时，卡会一直挂着。
