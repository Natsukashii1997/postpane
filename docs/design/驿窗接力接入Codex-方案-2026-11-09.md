# 驿窗接力接入 Codex：方案（#253，2026-11-09）

只是方案，没改代码。前提：#278（`8c2de38`）已经把上游 `b1217c3` 的送话层 `src/crates/platform/src/delivery/` 和智能体互发消息整体搬进驿窗，实机跑通了 Claude ↔ Codex 互发：Codex 收到消息、用 `send_message` 回信、回信回到原 Claude 会话（CURRENT.md #278 一节）。

## 一、结论

| Codex 在接力里的角色 | 建议 | 理由 |
|---|---|---|
| **审核方**（Claude 做完，交 Codex 审） | **不进接力，直接用 #278 的互发消息** | 接力的轮次、审查预算、「审查出口」那一套，是给 ChatGPT 网页定的（ROADMAP 阶段 5：ChatGPT 是审核主角）。Codex 审，Claude 用 `send_message` 发过去，Codex 回结论，已经能用；连续来回上限默认 10。以后真要给 Codex 审核加轮次和预算，再另开一单。 |
| **发起方**（Codex 做完，交 ChatGPT 审） | **做**，本单主要工作 | 现在 `relay_to_chatgpt` 只认 Claude Code。Codex 的调用方身份，MCP 中转本来就传过来了（`src/apps/mcp/src/index.ts` 的 `caller`），是驿窗在 `handoff.rs` 的 `relay` 里拒掉的（约第 1854 行）。 |
| **回信接收方**（ChatGPT 的回信转回 Codex） | **做**，和发起方一起做 | 发起方是 Codex，回信就得送回 Codex。用 delivery 的队列：`LocalClients::send`，加 `Operation::Enqueue`。不用 ROADMAP 原来写的 `steer-turn`，因为它会插进 Codex 正在跑的那一轮。 |

## 二、驿窗要改哪里

1. **接力数据**（`src/crates/platform/src/clients/chatgpt/handoffs.rs`、`handoffs.json`）
   - 现在只记 `claudeSession`。
   - 改成「发起方 = 客户端 + 会话 id」（`doer: {client, session}`）；旧记录读成 `client: "claude"`，不迁移文件。
2. **发起**（`host/src/handoff.rs` 的 `relay`）
   - 调用方是 Codex 时也收；会话 id 取 MCP 中转传来的 `caller.sessionId`，也就是 Codex 的线程 id，来自 `_meta.threadId`。
   - 驿窗不认识的客户端照旧拒，报错写明「只接 Claude Code 和 Codex」。
3. **回信通道**（`Lines` 这组接口：`reaches`、`reply`、`queue`、`left`、`opener`）
   - 现在这组接口只走 Claude 插件。改成按发起方的客户端分两路：
   - Claude 保持现状；
   - Codex 走 #278 起已经常驻的 `LocalClients`：
     - 发：`SendRequest { provider: codex, operation: Enqueue, request_id: "<接力 id>-<步号>" }`。用固定的 id，重发时会认出是同一条，不会送两遍；
     - 跟进度：`LocalClients::receipt`，排队 → 已领取 / 已开始，对上 #257 的「排队中 / 已领取 / 已开始」；
     - Codex 没开着那个线程时，delivery 自己会用 `codex://threads/wake/<id>` 唤醒，或者等它被打开（上游 `jazzenchen/agent-hud-open` 的 `docs/agent-messages.md` 第 34–35 行，驿窗没搬这份文档）。
4. **插话后轮数从 1 重算**（#258 那条，`opener`）
   - 对 Codex，要读 Codex 会话记录里当前这一轮是谁开的头：是驿窗送进去的（带 `agent-hud:` 开头的 id），还是常浩自己打的字。
   - 互发消息的 `messaging/src/transcript/` 已经有这套读法，可以复用。
   - 第一版要是做不到，就先按「不重算」处理，交接里写明。
5. **左滑发起**（侧栏「正在进行」里的 Codex 会话也能左滑「审核 / 讨论」，#128）
   - 发起那句话改用 Codex 队列送进去。
   - 这一条动的是已定的交互（见第四节），单独问。
6. **AI 接入**（P-13）
   - 「AI 接入」页和 AGENTS.md 的「发起方只认 Claude Code」改成 Claude Code、Codex；
   - 功能清单那一行写上 Codex 的接入方式（Codex 队列，`thread/queue/add`）。
7. **ROADMAP**
   - 第 83 行、第 138 行的 Codex 通道，从 `thread-follower-start-turn` / `steer-turn` 改成「delivery 队列（`thread/queue/add`），等空闲作为新一轮，不插话」。

## 三、风险

- **Codex 内部接口**：`thread/queue/add`、`thread-writer-locks/*.lock`、`codex://threads/wake/` 都不是公开接口，Codex 一升级就可能失效。2026-11-09 在 ChatGPT.app 内置 Codex（Codex Framework 157.0.8103.39）上实测可用。
  - 失效时，按 P-13「选定的执行方不可用时明确报错」：接力卡上写「转回 Codex 失败」，交还常浩，不自动换成别家。
- **会话 id**：Codex 的线程 id 和 Claude 的会话 id 格式不同。凡是按 `claudeSession` 找会话的地方（侧栏、展开卡、#223 迟到补绑）都要一起改，漏一处就会出现「找不到会话」。
- **测试**：现有接力测试的假通道是按 Claude 写的，要补一个 Codex 假通道。delivery 自带 `fixtures` 特性，可以直接用（`platform/Cargo.toml`）。
