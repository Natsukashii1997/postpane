## 二、智能体互相传话 × 驿窗接力

### 上游怎么做

总说明：上游 `docs/agent-messages.md`。

1. **开关**：默认关（`agentMessages`）。打开后 MCP 才列出 `list_sessions`、`send_message`、`start_session`、`get_message`。
2. **发送方身份**：由 MCP 中转程序认定，不收参数。Claude 读 `CLAUDE_CODE_SESSION_ID`，Codex 读 `_meta.threadId`（`apps/mcp/src/host-tools.ts:45,55`）。认不出就不发。
3. **先拒再记**：以下情况在写日志之前直接拒收（`messaging/src/send.rs:14-62`）：
   - 空文本
   - 来自手机
   - 发给自己
   - 找不到的会话或子会话
   - 对方此刻收不了
4. **回执与不盲重发**（`platform/src/delivery/sending.rs:17-35,70-75,113-118`）：
   - 每个会话一把锁，保证顺序。
   - 先写一条只含 SHA-256 指纹的 `uncertain` 回执，再调通道。
   - 同一 id、同样内容再来，返回原回执；同一 id、内容不同，报冲突。
   - 字节可能已经发出就绝不重发。只有「插件没签到」这种能证明没发出的失败，才能用原 id 再试。
5. **送进 Claude**：
   - 会话里的插件每 5 秒签到一次，一次签到 20 秒内有效。
   - 话放进共享文件夹，插件领走后等会话空闲再提交，1 小时没人领就过期。
   - 回执跟到「已领取 / 已开始 / 被拒」。
6. **送进 Codex**：
   - 传话一律用 `thread/queue/add`，带 `clientUserMessageId: agent-hud:<id>`。经共享守护进程或临时 `codex app-server` 送入，不加载线程，等空闲后作为新一轮。
   - 看 `thread-writer-locks/<thread>.lock` 判断有没有应用开着这个线程；没人开就用 `codex://threads/wake/<id>` 唤醒（`codex/unix/mod.rs:54-105`）。
   - 「桌面应用优先」只用于新一轮、插话、打断，**不用于传话**。
7. **链和轮次**（`send.rs:64-72,146-180`）：
   - 发送方这一轮如果是由驿窗送进去的消息开始的，就接着原链、轮次加 1。
   - 如果是用户自己开的这一轮，就开新链。
   - 超过上限（默认 10）拒收，等用户插话后重新计数。
8. **消息格式**（`words.rs:48-95`）：首行标签 `[Agent HUD · from <客户端> · <标题> · <id>]`，末行教对方怎么回；回复的末行写「只有还需要再说时才回」，防止两边来回道谢。
9. **取答案**：`get_message` 只读已采集的会话记录，按 id 或指纹找到那一轮，不唤醒会话。
10. **日志**：保留一周，只存指纹不存原文（`journal.rs:34-59`）。纸飞机每轮飞一次，被拒就半路掉落。

### 可学的（按价值）

1. **【现存缺陷，已核实】回 Claude 的「排队兜底」实际不起作用。**
   - `auto_back` 的流程：先 `reaches` + `reply` 直接送，失败再送一次，再失败就 `leave` 排队（`src/crates/host/src/handoff.rs:957-985`）。
   - 但 `reply` 和 `leave` 底下都调同一个 `hand()`（`handoff.rs:1489-1503`），而 `hand()` 会先检查会话 20 秒内有没有签到，没签到就返回 `NotLoaded`（`src/crates/platform/src/claude_plugin/mod.rs:345`）。
   - 所以会话一旦没签到（L-14 那种会话已结束的场景），三次尝试必然全部失败；会话签到正常时，第一次就已经送成了。兜底没有起作用的情况。
   - 单元测试的假通道不检查签到，测不出来。CURRENT 也记过「实机还没走过排队这条路」。
   - 改法：允许给没签到的会话留话（1 小时内有效），或先用 `claude://resume?session=` 唤醒再留话；驿窗已有 `navigation/claude_job.rs:58`。改动小到中。唤醒会把 Claude 桌面版拉到前台，要你定。
2. **回执状态机**：每一步用「接力 id + 步号」作固定 id，先写 `uncertain` 再发；回 Claude 用已有的 `left()` 跟到「已领取 / 已开始」。
   - 能替换现在只按 1 小时计时的排队（`chatgpt/handoffs.rs:913`）和 #223 的迟到补绑。
   - 要你拍板：上游「结果不明不重发」和驿窗「30 秒没回话算失败」冲突。
   - 改动量：中。
3. **Codex 接进接力（批 D）走队列，不走 steer**：ROADMAP 第 83 行写的是用 `steer-turn`，它会插进正在跑的一轮（上游 `codex/desktop.rs:117`），正是上游刻意不拿来传话的路线。
   - 应改用 `thread/queue/add` + writer lock 判断 + `wake` 唤醒。Codex 发起时身份取 `_meta.threadId`，回信靠 `agent-hud:<id>` 找到 Codex 回答的那一轮。
   - 改动量：中到大。风险：这是 Codex 内部接口，版本一变可能失效。
4. **用户插话自动重置轮次**：看当前这一轮是不是用户自己开的，是就重置，代替手动点「继续自动」（对应 L-21）。改动小。以后 Claude 和 Codex 直接互传时，必须有这种链式上限。
5. **消息首尾格式**：首行标签说明来源，末行教怎么回、「只有还需要再说时才回」。等 Claude 和 Codex 互传时直接可用。改动小。

### 不学或要改造

- ChatGPT 网页不是本机客户端，没有队列和签到。驿窗现有的 `opened` / `sent` / `turn complete` 已经是专门的回执。
- 「只存指纹」：驿窗转回和重试要用原文，最多改成过期后删除。
- `get_message` 拉取式取答案：驿窗是插件主动推送，对 ChatGPT 更合适；只有 Codex 当审核方时才需要。
- 「以我的名义发」、`claude --bg` 新开会话、Antigravity、DeepSeek、Windows 分支：用不上。

### #253 要修正的地方

- 第 1 点说错：上游传话不是「先交给桌面应用」，传话一律走队列。
- 第 3 点「等空闲才送达」：驿窗的 Claude 插件分叉前就有，不是新东西。
- 漏了：排队兜底失效、发送方身份认定、链和轮次、回信怎么读回来、`claude://resume` 唤醒、回执跟到领取。
